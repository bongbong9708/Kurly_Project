## AI 응답 요약

- 설계 선택지 A~G 제시, 추천안 표시
  - A. 화면 형태: `ContentUnavailableView` (추천) vs 직접 만든 VStack
  - B. 문구: 사용자 대응이 다른 경우만 구분 (추천) vs 하나로 통일
  - C. 다시 시도: 넣고, 최근 검색어를 다시 저장하지 않는 재요청 함수 분리 (추천) vs 넣지 않음
  - D. 빈 결과: 별도 화면 (추천) vs 빈 목록 유지
  - E. 403/429 구분: 헤더로 판별 (추천) vs 403 전부 Rate limit
  - F. WebView: 첫 로드 실패만 에러 화면 + 다시 시도, 취소(-999) 무시 (추천) vs 에러 화면만
  - G. 브랜치: WebView 에러를 #11에 (추천) vs #12에서 함께 → #11을 먼저 머지해 #12에서 함께 진행
- 테스트를 먼저 쓰고 컴파일 실패(`retry` 없음) 확인 → 구현
- E: 403은 `x-ratelimit-remaining: 0` 또는 `retry-after`가 있을 때만 `rateLimited`, 그 외 403은 `unexpectedStatus(403)`. 429는 그대로 `rateLimited`
  - **제안할 때는 `x-ratelimit-remaining`만 말했는데, 구현에서 `retry-after`(2차 한도) 조건을 AI가 추가함**
- C: `search()`의 요청 부분을 `load(keyword:)`로 분리. `retry()`는 마지막으로 요청한 검색어(`lastKeyword`)로 `load`만 호출
  - 실패 후 검색바 글자를 고친 경우에도 실패한 검색어로 다시 요청
- A·B: `SearchError+Message.swift`(Presentation)에 `title` / `message` / `systemImage`. 네트워크, 한도 초과, 그 외로 3가지
- D: `.loaded`인데 결과가 비면 "검색 결과 없음". `ContentUnavailableView.search`는 앱 언어(영어)로 나와 문구를 직접 지정
- F: Coordinator가 `didFailProvisionalNavigation`에서 `NSURLErrorCancelled`는 무시하고, 한 번도 로드에 성공하지 않았을 때만 `loadFailed = true`. 다시 시도는 `.id(attempt)`를 바꿔 WebView를 새로 만듦
- 시뮬레이터에서 Rate limit 화면 확인 시도
  - curl로 검색 한도를 소진 → 실제 응답이 `403` + `x-ratelimit-remaining: 0`임을 확인
  - 같은 시점에 앱의 새 검색(`swiftui`)은 성공. curl과 시뮬레이터가 다른 경로로 나가는 것으로 추정 (미확인) → 화면 확인 실패
