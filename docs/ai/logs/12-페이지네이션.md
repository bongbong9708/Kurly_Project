## AI 응답 요약

- 전제: 한 페이지 30개(API 기본값), 다음 페이지 실패는 목록 아래 인라인 + 받은 결과 유지(확정 결정), GitHub 검색은 1,000개까지만 주고 그 뒤 페이지는 422
- 설계 선택지 A~E 제시, 추천안 표시 → 추천안대로 결정
  - A. 요청 시점: 끝에서 5번째 행의 `onAppear` (추천) vs 마지막 행 vs 스크롤 위치 계산
  - B. 다음 페이지 판단 위치: ViewModel (추천) vs Domain UseCase
  - C. 상태: 기존 `State`와 별도로 `NextPageState` (추천) vs `.loaded`에 함께
  - D. 실패 후: 아래 "다시 시도" 버튼, 실패 중에는 스크롤로 자동 요청 안 함 (추천) vs 스크롤로 자동 재요청
  - E. 페이지 사이 중복 저장소: `id`로 빼고 붙임 (추천) vs 그대로
- 선택 없이 하기로 한 것: 하단 `ProgressView`, 새 검색·취소·다시 시도 시 다음 페이지 요청 취소, 로딩 중 추가 요청 막기
- 테스트를 먼저 쓰고 컴파일 실패(`loadNextPageIfNeeded` 없음) 확인 → 구현
- ViewModel
  - `NextPageState`(idle / loading / failed), `maxResultCount = 1000`, `prefetchThreshold = 5`
  - `loadNextPageIfNeeded(currentItem:)`: 보이기 시작한 행이 끝에서 5번째 안쪽이면 요청
  - `retryNextPage()`: 실패 상태일 때만 다시 요청
  - 다음 페이지 유무: 서버에서 받은 개수(중복 빼기 전)가 `min(total_count, 1000)`보다 적고, 마지막 페이지가 비어 있지 않으면 있음
  - 새 검색(`load`)과 검색어 비우기(`query` didSet)에서 `resetPagination()`으로 진행 중 요청 취소·상태 초기화
  - **논의 없이 AI가 정한 것**
    - 검색했던 검색어(`currentKeyword`)를 따로 저장. 검색 후 검색바를 고쳐도 다음 페이지는 원래 검색어로 요청하려고 (자동완성 작업에서 `lastKeyword`를 없앴던 것과 비슷한 값을 다시 둠)
    - 이어 붙일 때 `totalCount`는 첫 페이지 값을 유지
    - 다음 페이지 실패 안내 문구는 `SearchError.title` 재사용
- View: 결과 행에 `onAppear`로 `loadNextPageIfNeeded`, 목록 맨 아래 `nextPageFooter`(로딩 표시 / 실패 안내 + "다시 시도")
- 하단 로딩 표시가 두 번째 페이지부터 안 보이는 문제 (사용자가 발견)
  - **AI의 첫 확인은 첫 페이지 경계만 봐서 이 문제를 놓쳤다**
  - 재현: 화면 녹화 후 목록 끝이 보이는 프레임을 골라 확인. 첫 경계에는 로딩 표시가 있고, 두 번째 경계에는 아래 행은 생기지만 비어 있음
  - 원인 추정: `List`가 아래 행을 재사용하면서 `ProgressView`가 다시 돌지 않음 (SwiftUI 내부 동작이라 확인하지는 못함)
  - 수정: 아래 행에 `.id(result.repositories.count)`를 붙여 받은 개수가 바뀔 때마다 새 행으로 그리게 함
