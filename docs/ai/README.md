# AI 활용 기록

이 과제는 생성형 AI를 활용해 진행했다. 이 문서는 **어디에 AI를 썼고, 어디를 직접 판단했는지**를 정리한다.

## 사용 도구

| 도구 | 용도 |
|---|---|
| Claude (Claude Code) | 설계 논의, 코드 작성, 테스트 작성, 문서 정리 |

## 작업 원칙

레포 루트의 [CLAUDE.md](../../CLAUDE.md)에 AI에게 적용한 규칙을 정리해 두었다. 핵심은 다음과 같다.

- **코드보다 판단을 먼저 꺼낸다.** 선택지와 트레이드오프를 나열하게 하고, 최종 선택은 직접 한다.
- **필요한 만큼만 만든다.** 요청하지 않은 기능, 일어날 수 없는 상황을 위한 에러 처리는 넣지 않는다.
- **검증 가능한 목표로 바꾼다.** "되게 해줘"가 아니라 "이 테스트가 통과하면 끝"으로 바꿔서 지시한다.
- **설명할 수 있는 코드만 남긴다.** 비자명한 코드에는 "왜"를 주석으로 남기게 한다.
- **AI가 틀린 것을 기록한다.** 첫 제안의 문제를 숨기지 않는다.

## AI가 틀린 사례

기록 중 가장 중요한 부분이다. 테스트가 없었다면 그대로 넘어갔을 것들이다.

### 1. 검증하지 않은 가정으로 쓴 코드 ([01](logs/01-dto-디코딩.md))

AI는 `URL(string:)`이 잘못된 문자열에 `nil`을 돌려줄 것이라 가정하고, 변환 실패 시 항목을 버리는 코드를 작성했다.

실제로는 최신 Foundation의 `URL(string:)`이 공백을 자동 인코딩하고 scheme 없는 문자열도 상대 URL로 받아들인다. `nil`이 되는 입력은 사실상 빈 문자열뿐이라, 작성된 `guard`는 거의 동작하지 않는 코드였다.

**먼저 쓴 테스트 2개가 실패하면서 드러났다.** 이후 검증을 제거하고 `URL` 타입으로 직접 디코딩하도록 바꿨다.

### 2. 테스트를 통과하는데도 남아 있던 설계 결함 ([02](logs/02-api-client.md))

AI는 모든 네트워크 호출 실패를 `SearchError.network` 하나로 묶었다. 테스트는 전부 통과했다.

PR 리뷰 지점을 설명하는 과정에서, 이전 요청을 취소했을 때 발생하는 `URLError(.cancelled)`까지 네트워크 에러가 된다는 것이 드러났다. 그대로 두면 **새 검색어를 입력할 때마다 에러 화면이 뜨는 동작**이 됐을 것이다.

취소는 실패가 아니라 정상 흐름이므로 `SearchError.cancelled`를 분리했다.

### 3. 문서 간 충돌 ([00](logs/00-과제분석.md))

AI가 제안한 내용이 이미 기록해둔 결정과 어긋난 경우가 있었다. 기록이 쌓일수록 AI 제안이 기존 결정과 맞는지 직접 확인해야 했다.

### 4. 확인 범위가 좁아 놓친 화면 버그 ([12](logs/12-페이지네이션.md))

AI는 페이지네이션 하단 로딩 표시를 첫 번째 페이지 경계에서만 확인하고 완료로 보고했다.

이후 **두 번째 페이지부터 로딩 표시가 보이지 않는다는 것을 직접 발견했다.** 화면 녹화로 재현해 보니 `List`가 하단 행을 재사용하면서 `ProgressView`가 다시 돌지 않았다. 하단 행에 받은 개수로 `.id`를 줘서 매번 새로 그리게 고쳤다.

### 5. 요청과 다른 곳에 만든 상태 ([11](logs/11-자동완성.md))

"입력 중인지"를 판단하는 상태를 AI는 ViewModel의 `isEditing`으로 만들었다. 원했던 것은 텍스트 필드의 편집(포커스) 상태를 쓰는 것이었다.

SwiftUI `TextField`에는 `isEditing`이 없고, `.searchable` 검색바의 포커스를 읽는 `.searchFocused`는 iOS 18부터라 최소 지원 버전(iOS 17)에서는 쓸 수 없었다. `isSearchPresented` → ViewModel 상태 → 키보드 표시 알림 순으로 세 번 바꾼 끝에 정리됐다.

### 6. 행 탭을 막은 제스처 ([11](logs/11-자동완성.md))

"빈 곳을 누르면 키보드를 내린다"를 AI는 목록 화면 전체에 탭 제스처를 붙여 구현했다.

시뮬레이터에서 자동완성 행을 눌러도 검색이 되지 않았다. 제스처를 뺐을 때 행 탭이 되는 것을 확인해 원인을 좁혔고, 제스처는 행이 없는 안내 화면에만 붙였다.

### 7. 작업 사이에 어긋난 기준 ([13](logs/13-다시시도-검색어.md))

자동완성 작업에서 "다시 시도"는 검색바 글자로 요청하도록 바뀌었고, 이후 페이지네이션 작업에서 AI가 "다음 페이지는 검색했던 검색어로 요청"하는 값을 새로 만들었다. 각 작업의 테스트는 통과했지만 두 기능의 기준이 달라졌다.

전체 점검에서 드러났고, 다시 시도도 같은 검색어를 쓰도록 통일했다.

### 8. 논의 없이 넣은 것 ([10](logs/10-에러-처리.md), [11](logs/11-자동완성.md), [12](logs/12-페이지네이션.md))

AI가 제안 때 말하지 않은 것을 구현에 넣은 경우가 있었다. 403 판별의 `retry-after` 조건, `query`가 실제로 바뀔 때만 입력 중으로 보는 조건, 다음 페이지용 검색어 저장 등이다. AI가 보고에 드러내 적었기 때문에 확인할 수 있었다.
