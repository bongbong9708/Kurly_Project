# AI 활용 기록

이 과제는 생성형 AI를 활용해 진행했다. 이 문서는 **어디에 AI를 썼고, 어디를 직접 판단했는지**를 정리한다.

## 사용 도구

| 도구 | 용도 |
|---|---|
| Claude (Claude Code) | 설계 논의, 코드 작성, 테스트 작성, 문서 정리 |

## 작업 원칙

레포 루트의 [CLAUDE.md](../../CLAUDE.md)에 AI에게 적용한 규칙을 정리해 두었다. 핵심은 다음과 같다.

- **코드보다 판단을 먼저 꺼낸다.** 선택지와 트레이드오프를 나열하게 하고, 최종 선택은 직접 한다.
- **필요한 만큼만 만든다.** 요청하지 않은 기능, 일어날 수 없는 상황을 위한 에러 처리는 넣지 않는다.
- **검증 가능한 목표로 바꾼다.** "되게 해줘"가 아니라 "이 테스트가 통과하면 끝"으로 바꿔서 지시한다.
- **설명할 수 있는 코드만 남긴다.** 비자명한 코드에는 "왜"를 주석으로 남기게 한다.
- **AI가 틀린 것을 기록한다.** 첫 제안의 문제를 숨기지 않는다.

## AI가 틀린 사례

기록 중 가장 중요한 부분이다. 테스트가 없었다면 그대로 넘어갔을 것들이다.

### 1. 검증하지 않은 가정으로 쓴 코드 ([01](logs/01-dto-디코딩.md))

AI는 `URL(string:)`이 잘못된 문자열에 `nil`을 돌려줄 것이라 가정하고, 변환 실패 시 항목을 버리는 코드를 작성했다.

실제로는 최신 Foundation의 `URL(string:)`이 공백을 자동 인코딩하고 scheme 없는 문자열도 상대 URL로 받아들인다. `nil`이 되는 입력은 사실상 빈 문자열뿐이라, 작성된 `guard`는 거의 동작하지 않는 코드였다.

**먼저 쓴 테스트 2개가 실패하면서 드러났다.** 이후 검증을 제거하고 `URL` 타입으로 직접 디코딩하도록 바꿨다.

### 2. 테스트를 통과하는데도 남아 있던 설계 결함 ([02](logs/02-api-client.md))

AI는 모든 네트워크 호출 실패를 `SearchError.network` 하나로 묶었다. 테스트는 전부 통과했다.

PR 리뷰 지점을 설명하는 과정에서, 이전 요청을 취소했을 때 발생하는 `URLError(.cancelled)`까지 네트워크 에러가 된다는 것이 드러났다. 그대로 두면 **새 검색어를 입력할 때마다 에러 화면이 뜨는 동작**이 됐을 것이다.

취소는 실패가 아니라 정상 흐름이므로 `SearchError.cancelled`를 분리했다.

### 3. 문서 간 충돌 ([00](logs/00-과제분석.md))

AI가 제안한 내용이 이미 기록해둔 결정과 어긋난 경우가 있었다. 기록이 쌓일수록 AI 제안이 기존 결정과 맞는지 직접 확인해야 했다.
